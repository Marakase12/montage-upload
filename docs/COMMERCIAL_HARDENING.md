## Что меняется

### Сохранность хранилища

- API больше не запускает массовое удаление объектов при старте и каждый час.
- `POST /api/admin/cleanup` теперь только считает объекты. Всегда возвращает
  `dryRun: true`, `deletionEnabled: false`; параметра включения удаления нет.
- Отчёт не выдаёт имена/ключи объектов, не удаляет служебные записи и не прерывает
  multipart-загрузки. Обход ограничен страницами и общим таймаутом; неполный отчёт
  явно помечается `truncated`.
- `GET /api/admin/auth-check` проверяет административный ключ без обращения к S3
  или БД; неверный ключ получает 401. Ответы не кэшируются.

**Ограничение:** отсутствие этого cleanup не продлевает срок доступа через API
и не отменяет внешние lifecycle-правила S3. Физический объём и расходы могут расти.
Нужна отдельная политика хранения по проекту (S17); этот отчёт не является планом удаления.
Явная отмена пользователем своей загрузки и удаление некорректной загрузки сохранены.

### Владелец задачи и память

| Сценарий | Доверенный owner | Область постоянных предпочтений |
|---|---|---|
| Новая загрузка авторизованного аккаунта | `account` + серверный UUID | Этот аккаунт, включая другие его проекты |
| Гостевая или Telegram upload-link загрузка | `guest` + точный jobId | Только этот проект |
| Старая задача без owner | `guest` + точный jobId | Только этот проект, без копирования личной памяти |
| Гостевой проект добавлен в кабинет после загрузки | Owner исходной задачи сохранён | Прежняя гостевая область этой задачи |

Новый owner берётся из проверенного серверного токена проекта, затем сохраняется
в подписанной сессии загрузки и серверной очереди. Поля формы, имя файла и текст
правки не определяют владельца. Для правок и approval используется owner исходной
записи очереди, а не новый токен после присоединения проекта к аккаунту.

После добавления гостевого проекта в кабинет прежний гостевой API-токен должен
быть отклонён на всех project-token endpoints. Это не мгновенный отзыв уже
выданных прямых S3 URL: они живут до собственного короткого срока истечения.
Полный отзыв всех ранее выданных возможностей доступа — отдельная задача S19.

В Python имя профиля вычисляется как `cloud-account-<sha256>` или
`cloud-guest-<sha256>`. Этот зарезервированный формат не совпадает с Telegram-ником.
Профиль `marakase` для облачных задач больше не используется. Файлы других
пользователей не переносятся и не объединяются. Технические defaults остаются общими;
постоянные предпочтения сохраняются только при явной просьбе пользователя.

Это логическая изоляция внутри доверенного worker, **не** отдельная ОС-песочница
для каждого клиента. Служебный worker-ключ всё ещё имеет широкий доступ.

### Проверка принадлежности ролика

До AI-плана, правок и approval проверяются cloud jobId/taskId, локальный путь
непосредственно внутри `jobs`, точный `ingest_scope` и неизменность `cloud_identity`.
Если соответствие не доказано, операция завершается ошибкой, а не ищет «похожий» ролик.
Старый source.json получает привязку только при точном совпадении cloud-scope.
Исходное видео не изменяется. Историческое имя автора старого website-approval
сохраняется; его отзыв требует уже подтверждённой привязки. Для Telegram-approval
это исключение не применяется. Сам approval не запускает публикацию.

Старая очередь без owner совместима; очередь без исходной записи или с неверным
owner не получает разрешение на правки. Старый journal сохраняет fingerprint
и отдельно проверяет новый cloudIdentity при восстановлении.

### Совместимость версий

API требует числовой целочисленный `bridgeVersion >= 3` при захвате новой задачи
или действия. Старый worker получает `426 / WORKER_UPGRADE_REQUIRED` **до** чтения
или изменения очереди на этих endpoints. Heartbeat и завершение уже взятой работы
не блокируются этим правилом. Проверка версии — защита от несовместимой выкладки,
не замена авторизации worker-ключом.

В `/api/health` проверяются `release`, `minimumBridgeVersion: 3` и
`ownerIsolationVersion: 1`. Живой worker нужно отдельно проверить локальной
диагностикой: наличие нового файла на диске не доказывает, что старый процесс обновился.

## Локальная проверка

Из `X:\AI\montage\upload-service`:

```powershell
node --check public/app.js
node --check public/config.js
node --check timeweb-api/server.js
node --test
git diff --check
```

Из `X:\AI\Codex\montage`:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Тесты изоляции используют временные каталоги и подменённые сервисы: не обращаются
к пользовательским роликам, AI, Telegram, production-БД или S3. Не включать
необязательный настоящий render-smoke без отдельного тестового исходника и решения.

GitHub workflow `checks.yml` запускает Node-тесты для PR и как обязательную
зависимость Pages-deploy. Установка идёт по lockfile, без install scripts.
Python находится в отдельной локальной папке и **не покрыт этим GitHub workflow**.
Timeweb deployment тоже не блокируется им автоматически: проверка перед выкладкой
API остаётся отдельным обязательным шагом. Первый удалённый запуск CI для
`92f4175` прошёл; Pages-deploy стартовал после успешного `checks / test`.

## Порядок выкладки — отдельная операция

1. Согласовать короткое окно обновления. Проверить текущую задачу и очередь.
2. Сохранить защищённую резервную копию изменяемых метаданных/preferences и
   совместимый комплект старого кода. Не класть ключи, media или runtime в Git.
3. Запросить штатную остановку bridge **между** задачами и дождаться выхода.
   Проверить, что планировщик не запустит старый экземпляр повторно.
   Команды из рабочей папки, только во время этой согласованной операции:

   ```powershell
   .\.venv\Scripts\python.exe cloud_bridge.py --diagnostics
   .\.venv\Scripts\python.exe cloud_bridge.py --request-stop
   ```

4. Опубликовать проверенный Git-коммит и подтвердить CI; отдельно обновить
   основное Timeweb-приложение **256921**. Legacy-приложение **256355 не запускать**.
5. Проверить health-маркеры, готовность аккаунтов и read-only admin-auth-check.
   Ключ брать из защищённого локального источника, не вставлять в команду/чат/лог.
6. Проверить на Windows комплект `cloud_bridge.py`, `cloud_identity.py`,
   `preference_store.py`, `approve_job.py` и их локальные тесты. Запустить один
   bridge существующим способом, без повторной регистрации/перезаписи планировщика.
7. Диагностика должна показать версию 3 живого процесса. Проверить heartbeat и
   отсутствие второго экземпляра. Затем согласованный smoke: два тестовых аккаунта,
   загрузка → обработка → скачивание; правка с «запомни» не меняет другой аккаунт.
8. Только после реальных подтверждений поменять соответствующие LOCAL на PROD.

Не перезапускать посреди рендера. Не очищать очередь или journals ради запуска.
Если старые метаданные не проходят проверку, остановить конкретную операцию и
разобрать причину без угадывания владельца. Автоматический повтор approval/публикации запрещён.

## Откат и оставшиеся ограничения

- При несовместимости безопаснее оставить обработку на паузе, чем разрешить старый
  общий профиль. Не отключать version gate для ускорения запуска.
- Старый API с массовой очисткой нельзя просто развернуть обратно на том же bucket.
  Откат должен сохранять отключённую разрушительную очистку и совместимость identity.
- Сохранённые cloud_identity не удалять для обхода ошибки и не заменять username
  на личный профиль. Техническую миграцию делать отдельно с проверкой происхождения.
- Общий ingest ещё может остановиться из-за повреждённого чужого source.json;
  новая identity-проверка такие чужие файлы пропускает, но весь ingest этим не исправлен (R09).
- Идемпотентность завершения загрузки, атомарные квоты, retention по проекту,
  отдельное окружение, ротация S3/БД и перенос worker на сервер — следующие задачи,
  а не обещание готовности в этом пакете.

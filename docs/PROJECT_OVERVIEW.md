# MontageAI — карта проекта

Дата проверки исходников: 2026-09-22. Документ описывает код и известные границы,
а не заменяет проверку работающего production. Новые изменения безопасности пока LOCAL.

## Назначение

MontageAI помогает подготовить короткий ролик либо выбрать самостоятельные
фрагменты длинного видео, оформить их, получить preview и внести правки обычным
языком. Редакторские решения AI проходят через ограниченный план; работу с файлами,
субтитрами, FFmpeg и проверкой результата выполняет детерминированный исполнитель.

Главный результат для клиента — пригодный ролик с сохранённым смыслом и понятным
состоянием обработки. Процент выполнения, наличие MP4 или ответ AI сами по себе
не доказывают готовность результата.

## Где находится код

| Компонент | Расположение на рабочей машине | Основные точки входа |
|---|---|---|
| Сайт и облачный API, Git-репозиторий | `X:\AI\montage\upload-service` | `public/app.js`, `timeweb-api/server.js` |
| Детерминированный Python pipeline | `X:\AI\Codex\montage` | `process_video.py`, `process_long_video.py`, `render_preview.py` |
| Мост между облаком и исполнителем | Python-проект | `cloud_bridge.py`, `cloud_identity.py` |
| Telegram и локальное управление | Python-проект | `telegram_worker.py`, `web_panel.py`, `montage` |
| Аккаунты и миграции | Web/API-проект | `timeweb-api/accounts.js`, `timeweb-api/migrations/` |
| Безопасность и очереди | Web/API-проект | `pipeline-owner.js`, `pipeline-runtime.js`, `storage-cleanup.js` |

Python-папка сейчас не является частью этого Git-репозитория. Публикация сайта
сама по себе не обновляет Windows worker. Это отдельный риск воспроизводимости (C01).

## Текущая схема

```text
Браузер / iPhone ──→ сайт и API ──→ аккаунты / проекты в PostgreSQL
        │                 │
        └─ signed upload ─┴──→ приватное S3: исходники, queue/status/action JSON
                                      │
                                 Windows bridge
                                      │
                          Python → Whisper / AI → FFmpeg
                                      │
                              проверенный preview
                                      └──→ S3 → сайт → правка / download / approval

Telegram → локальный Telegram worker → тот же Python pipeline
```

Сайт и облачная загрузка уже существуют. Пока персональный компьютер выполняет
тяжёлые стадии и хранит рабочие артефакты. Закрыть браузер после подтверждённой
загрузки и выключить компьютер с worker — разные действия: второе останавливает
исполнение. Цель переноса — убрать именно эту зависимость.

Веб-интерфейс и API могут обслуживаться одним Timeweb-приложением; GitHub Pages
остаётся существующей отдельной статической точкой входа. Для аккаунтов целевой
путь — один HTTPS origin, не набор случайных локальных адресов.

## Что подтверждается текущим кодом

- Приём MP4/MOV/MKV и прямая multipart-загрузка в S3.
- Аккаунты, сессии и привязка проектов; SQLite не является облачной account-БД.
- SHORT: ffprobe, тайминги слов, AI-анализ/hook, субтитры, музыка, render и validation.
- Форматы 9:16, 1:1 и 16:9; необязательное кадрирование одного говорящего.
- LONG-анализ и объяснения выбора кандидатов; Telegram умеет запускать выбранные
  фрагменты. Полноценный выбор/рендер LONG-кандидатов на сайте ещё нужно завершить.
- Правки и отдельное подтверждение preview. Публикация не запускается.
- Heartbeat, аренда начальной задачи, ограниченное восстановление и отдельные
  ключи результатов попыток. Нельзя автоматически повторять неоднозначный approval.
- Локально подготовлены разделение cloud-предпочтений, защита владельца,
  отзыв guest API-доступа после claim и отключение массовой автоматической очистки.

Работоспособность функции в исходниках не равна подтверждению её текущего deploy.
Проверки релиза и статусы находятся в коммерческом бэклоге и runbook.

## Где сейчас истина о данных

| Данные | Сейчас | Целевое направление |
|---|---|---|
| Пользователь, сессия, проект | PostgreSQL в облачном варианте | PostgreSQL |
| Очередь, статус, действие, heartbeat | S3 JSON; переходы сериализуются через PostgreSQL locks | Постепенная транзакционная модель в БД |
| Исходник / доступный результат | S3 и рабочая копия у исполнителя | Приватное S3 + проверяемый manifest |
| Transcript, планы, локальные jobs | Диск Windows | Durable worker storage, затем переносимые артефакты |
| Постоянные настройки | Локальные preference-файлы | Версионируемая память аккаунта через API/БД |

Нельзя сейчас объявлять PostgreSQL единственной истиной для всего pipeline:
переход ещё не выполнен. Нельзя считать диск контейнера надёжным хранилищем.

## Неизменяемые правила

- Исходник неизменяемый; обычный SHORT не обрезается без просьбы.
- USER start/anchor имеет приоритет. Удаление пауз — по запросу.
- LONG не обязан выдавать фиксированное число роликов; фрагмент должен иметь
  законченный смысл. Отклонения и ошибки кандидатов показываются отдельно.
- Hook интригует, но не добавляет несуществующие факты и не обещает охваты.
- «Музыку тише» меняет текущий ролик; «…и запомни» — ещё и личные предпочтения.
- Повтор запроса не должен дублировать задачу или сбрасывать готовый результат.
- Только явное подтверждение конкретного результата разрешает будущую публикацию.
- Ни текст пользователя, ни transcript не становятся shell-командой.
- Ключи, подписанные URL и пароли не попадают в логи и документы.

## Чего пока не обещаем клиентам

Независимость от личного ПК, гарантированный срок обработки, SLA, неограниченное
хранение, email recovery, платёжную систему, multi-speaker crop и автоматическую
публикацию. Эти функции требуют отдельных этапов и реальных подтверждений.

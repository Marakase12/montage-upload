# Стабильность для первых клиентов

Дата: 2026-09-22. Выбранный пользователем приоритет — стабильность, затем новые
продуктовые функции. Это план приёмки; статусы находятся в [бэклоге](COMMERCIAL_BACKLOG.md).

## Что считаем стабильной услугой

Клиент может понять, принят ли файл, что сейчас происходит, где результат и как
повторить безопасную операцию. Сбой сети или процесса не меняет владельца, не
обнуляет готовую работу, не создаёт двойную задачу и не приводит к публикации.
Неизвестный результат обозначается как неизвестный, а не как успешный.

## Ближайшая очередь

### 1. Закончить и отдельно выложить пакет безопасности — S03–S12, S21–S22

- Изолированные настройки аккаунтов и гостей, проверка job/owner перед правкой.
- Старый guest API-token больше не работает после присоединения проекта к аккаунту.
- Старый worker не получает новые задачи нового протокола.
- Нет массового удаления S3 при старте/по таймеру.
- Полные локальные проверки, затем согласованный deploy и реальный smoke.

Локальная проверка 2026-09-22: Node — 113 успешных тестов; Python — 72 успешных,
1 необязательный render-тест пропущен. Это не проверка production или отдельного сервера.
Сценарий отказа на чужой retry дополнительно проверяет отсутствие изменений в очереди.

### 2. Повтор завершения загрузки без повторной обработки — R01

Сейчас маршрут завершения последовательно делает multipart complete, проверку
объекта, запись queue и запись status. Между этими действиями возможен обрыв.
Не считать следующий HTTP-запрос новой загрузкой только из-за потерянного ответа.

Проектируем контракт:

- Один подписанный upload/session ID → один исходник и одна pipeline task.
- Завершение и worker claim согласуются одной областью блокировки; два запроса
  complete не могут одновременно пересоздать состояние.
- Сохраняется подтверждение завершения с неизменной идентичностью загрузки.
- После потери ответа проверяется существующее подтверждение/объект/задача,
  а не безусловно повторяется вся цепочка.
- `READY_FOR_REVIEW`, `APPROVED`, `PROCESSING` и результат не заменяются на `QUEUED`.
- Частично записанная queue/status восстанавливается только при доказанном
  соответствии исходной сессии, владельца и файла; чужие записи не исправляются.
- S3 timeout/403 не трактуются как «файла нет». Проверка размера необходима,
  но не заменяет проверку идентичности; ETag не объявляется SHA-256 файла.
- Повтор не создаёт второе уведомление/списание. Неоднозначную доставку сообщения
  не маскировать обещанием exactly-once без соответствующего протокола.
- Frontend сохраняет upload/session при неоднозначном complete. Явный повтор
  использует тот же upload, не создаёт новый проект и не отправляет все байты заново.

Обязательные тесты: два одновременных complete; ответ потерян после S3 complete;
сбой после queue до status; сбой после подтверждённой записи status; повтор после
готового preview и approval; просроченная/чужая session; отсутствие S3-объекта;
S3 недоступен; повтор после guest→account claim; refresh страницы на iPhone.

**R01 пока не реализован этим документом.** Это следующий пакет кода, отдельно
от уже работающего retry начальной обработки FAILED.

### 3. Не дать одному плохому заданию остановить остальных — R04, R09

Проверить лимиты длительности, размера, числа потоков, scratch-диска, RAM и времени
каждой тяжёлой стадии. Ошибка одного source.json должна блокировать только его
восстановление, а не поиск других jobs. Не чинить чужой manifest догадкой.

Приёмка: повреждённое видео, битый JSON, недостаток диска, зависший AI/FFmpeg;
понятная ошибка конкретного job, worker жив и следующий допустимый job проходит.
Убийство процесса должно быть ограничено собственным процессом задачи.

### 4. Честный статус и поддержка — U02, S20, R07

- Разделить передачу файла, проверку загрузки, ожидание worker и обработку.
- 100% передачи не значит 100% монтажа. «Готово» только после проверки результата.
- OFFLINE/UNKNOWN worker не выдавать за ошибку самого видео.
- При сбое дать безопасный код обращения и конкретный следующий шаг.
- Не показывать сырые traceback, токены, подписанные URL и личные пути.
- Автоматические оповещения оператору только об изменении/необходимом действии,
  а не каждую минуту одинакового состояния.

### 5. Граница публичного пилота — S16, S17, R02, C08–C10

Перед платными клиентами: проверенное восстановление данных; политика хранения;
лимит нагрузки/расходов; учёт доступа; рабочий серверный executor либо явное
ограничение пилота на доступность личного ПК. Email recovery и поддержка клиента
нужны до обещания полноценного самообслуживания.

## Проверки перед выпуском

| Сценарий | Ожидаемое доказательство |
|---|---|
| Два клиента одновременно | Чужие проекты, ссылки и preferences недоступны |
| Двойной клик / повтор запроса | Одна задача, одно логическое завершение |
| Интернет пропал на последнем шаге | Исходник не требуется загружать заново при подтверждённом сохранении |
| Worker перезапущен | Начальная задача восстанавливается в разрешённых границах, actions не переигрываются |
| Правка готового ролика | Не выполняется ненужная транскрипция, новый результат проверен |
| Отсутствующий/просроченный результат | Нет ложной кнопки скачивания «готового» файла |
| LONG: семь кандидатов, четыре результата | Видно состояние каждого кандидата и причина остальных трёх |
| Approval | Подтверждён конкретный результат; публикация не вызвана |
| Личный ПК выключен | После C10 полный сценарий работает на сервере |

## Метрики пилота — предложения, не текущий SLA

Собирать фактические время загрузки, ожидания и стадий, долю технически успешных
jobs, число ручных вмешательств, стоимость успешного ролика и число правок до
скачивания. В знаменателе всегда указывать все принятые задания; неподдерживаемые
входы учитывать отдельно, не скрывать их для красивого процента.

Для закрытого пилота предложен набор: 20 разных SHORT + 5 LONG, два тестовых
аккаунта, несколько сетевых обрывов и перезапусков; затем 7 дней наблюдения.
Это стартовая проверка, не статистическое доказательство надёжности для тысяч людей.
Ноль пересечений данных, неожиданных публикаций и сбросов готовых результатов —
обязательный критерий. Временные и денежные цели согласовать после измерений.

## Чего не делать ради скорости

Не отключать проверки владельца/approval, не увеличивать бессрочно таймауты,
не очищать очередь целиком и не маскировать FAILED повторным автоматическим рендером.
Не покупать большой GPU-сервер до измерения узкого места. Не добавлять эффекты
вместо устранения подтверждённой причины потери загрузки.
